## 当前实现：多模型数据流

以下路径相对 `project1/demo_multhread_decode_infer_mulmodel/`。

```mermaid
flowchart LR
    A[文件或网络输入] --> B[StreamLoader / FFmpeg 读包]
    B --> C[MppDecoder 解码]
    C --> D[回调转换为 BGR / Mbuffer.img]
    D --> E[rknn_infer / 多模型任务]
    E --> F[DetectionFusionManager 融合与绘制]
    F --> G[images 每路最新结果]
    G --> H[combineImage 拼图]
    H --> I[StreamingManager 队列]
    I --> J[MPP H.264 编码 / FFmpeg FLV封装 / RTMP]
```

| 文件与符号 | 职责及数据 |
| --- | --- |
| `main.cpp::main` | 读取 `argv[1]` 为通道数，初始化并启动推流，创建每路 loader 和推理线程，再创建拼图线程 |
| `include/stream_loader.h::StreamLoaderManager` | 单例持有 URL 表、loader 裸指针和解码线程；当前启用的输入是相对路径本地 MP4 |
| `lib/stream_loader.cpp::StreamLoader::open/read_frame/operator()` | FFmpeg 打开输入、寻找视频轨、读取压缩包；H.264 分支使用 Annex B 过滤器；调用 MPP；按状态执行重新打开逻辑 |
| `lib/mpp_decoder.cpp::MppDecoder::Decode` | 获取 MPP 输出帧，在释放帧前同步调用解码回调 |
| `lib/stream_loader.cpp::mpp_decoder_frame_callback` | 按 stride 拷贝 YUV，按 NV12 转 BGR；优先 RGA，失败回退 OpenCV；在互斥锁内更新 `Mbuffer.img` |
| `main.cpp::rknn_infer`、`include/rknnPool.hpp::rknn_lite::interf` | 克隆输入图像，提交模型任务；执行 RGB 转换、缩放、RKNN 输入/运行/输出、后处理和画框 |
| `lib/detection_fusion_manager.cpp` | `main.cpp` 调用 `fuseDetections` 和 `drawFusedDetections` 合并并绘制检测结果；具体融合算法本轮未展开 |
| `main.cpp::combineImage` | 每路缩放为 640×360，拼成 1280×1080 图；RGA 失败回退 OpenCV；按目标 24 fps 提交输出，无新图时复用上一帧 |
| `lib/streaming_manager.cpp::streamingWorker/sendRTMPFrame` | 消费队列，必要时调整到配置的 1280×720，调用 `MppEncoder::EncodeFrame`，经 FFmpeg 写出 RTMP |

`initializeRTSP` 和 `sendRTSPFrame` 当前仅返回成功，属于占位实现，不能写成 RTSP 输出已完成。当前 `main` 启用 person、helmet、callplay 三个模型，tired 对应指针为空。

## 当前实现：线程、缓冲与所有权

- 每路 `load_stream` 创建一个执行 `StreamLoader::operator()` 的线程。解码回调在 `Decode` 调用链中执行；回调中的本地文件限速 sleep 会占用该路读取/解码线程。
- 每路还有一个 `rknn_infer` 线程，内部创建 `ThreadPool(4)`。各模型 future 完成后执行融合，再在 `mutexes[i]` 保护下发布到 `images[i]`。
- `Mbuffer.img` 是最新帧槽位，生产者替换，消费者在 `buffer.mtx` 内 clone；没有逐帧消费编号，因此推理循环次数不等于源视频帧数。“隔次推理”不能直接称为准确的源帧跳帧策略。
- MPP 输出的 `data` 在回调中借用，回调返回后输出帧被释放；回调将像素复制到自己的 YUV/BGR 缓冲。不要把该指针跨回调保存为持久图像。
- `p1->ori_img` 克隆自解码图像，但 p2/p4 的赋值共享 p1 的像素。`interf` 会写图画框，因此当前多模型并行路径存在共享像素读写风险；future 汇合不保护此前的并行写入。尚未做运行复现。
- `images[i]` 同样保存最新结果，拼图线程在对应互斥锁内 move 取走并清空。图像可能被覆盖，不保证每次推理结果都会输出。
- 拼图线程的 DMA tile 由 `dma_buf_alloc` 分配，`cv::Mat view` 包装外部内存。释放代码在无限循环之后，正常控制流没有到达它的出口。
- 推流是另一条队列：`addStreamingData` 在入队前检测 `size() > 10` 并丢弃最旧元素，随后 push；从空队列出发实际可达到 11 项。不能描述成容量严格为 10。
- 入队复制 `StreamingData`，其中 `cv::Mat` 共享像素；当前主链设置 `use_dma=false`，worker 再 clone。结构体有 DMA 字段不代表主链已经实现端到端零拷贝。

## 当前实现：错误与退出边界

- `StreamLoader::operator()` 根据 `status` 决定重开；网络失败重试间隔 10 秒，本地失败间隔 100 毫秒。内部重试循环未检查停止标志，不能保证停止请求及时生效。
- `load_stream` 调用 `open` 后未按返回值阻止线程启动。`read_frame` 的 bool 返回与 `status` 也不是所有错误路径都一致，不能笼统写成“错误统一恢复”。
- `combineImage` 为无停止条件的 `while(true)`，主线程先 join 它，后面的停止推流和卸载代码没有正常到达路径。
- 即使未来添加拼图出口，现有顺序仍是先 `unload_stream` 删除 loader，再 join 会访问 loader 的推理线程，需要一起核对生命周期。模型以 `new` 创建，当前 main 未看到对应 delete。
- 单模型入口同样保留了被注释掉的停止与 join 代码；它的窗口退出不等于整条流水线已经正常退出。

以上是源码定位线索，不是一次完整审查或板端故障复现。
